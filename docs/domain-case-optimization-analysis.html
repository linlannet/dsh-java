一、三项目 domain/case 设计速览

先给结论性判断：dsh-java 在"六边形纯度"和"模型充血度"上是三者里最好的，但在"事务边界"上是三者里最差的。两个参考项目正好提供了"策略树 + 责任链 + Map 策略"这套编排范式的成熟样本，以及"领域事件端口化"的可借鉴写法。

一句话总评：dsh-java 的 domain 内核是三者里最"DDD 正统"的（纯净、充血、事件溯源设施齐全、手工 wire 可测），但它的工程化短板（零事务、事件空转、线程池无界、O(n²) 重建）也恰好集中在 domain 内部——"骨架最正、落地未焊牢"。

二、dsh-java 已具备的优势（应保持）

这些是对照后发现 dsh-java 已经领先于两个参考项目的地方，优化时不要破坏它们。

保持1. domain 零 Spring 注解，真正的纯净六边形内核

实测 dsh-java-domain/ 下对 import org.springframework|jakarta.annotation 零命中。所有 @Service/@Resource/@Bean 都在外围（infrastructure 的 HarnessApplicationConfig + case/trigger 的组件扫描）。两个参考项目都做不到这点——它们的 domain 直接 @Service 满天飞，无法脱离 Spring 跑纯单测。

佐证：domain/agent/service/ReactLoopAgent.java、domain/session/registry/model/aggregate/HarnessSessionAggregate.java 均为纯 POJO

保持2. 充血模型 + 真实聚合根

ReactLoopAgent 是带生命周期行为（kick/turn/step/cancel）+ Phase 状态机的富实体；HarnessSessionAggregate 的 prepare()/changeStatus() 带 Objects.requireNonNull 守卫。两个参考项目的聚合根都是 @Data 贫血篮子（ai-mcp-gateway 甚至 aggregate 包只有 package-info）。

保持3. 事件溯源设施（ISessionEventStore 双适配器）

domain 有 SessionEvent/SessionLog/SessionRebuilderService/SurfaceProjector 完整事件溯源模型，端口 ISessionEventStore 有 JDBC + JSONL 两个适配器。这比 ai-mcp-gateway 的 ISessionPort（只是 Redisson pub/sub）更"DDD 原教旨"。问题只在于它没被接通（见下文 P1）。

保持4. 仓储端口以聚合根为参数，PO 映射下沉

IHarnessSessionRepository.save(HarnessSessionAggregate) 直接吃聚合根，infrastructure/.../HarnessSessionRepository 才做 聚合 ↔ HarnessSessionPO 转换。领域层看不到 SQL/MyBatis，标准六边形。

保持5. 手工 @Bean 构造注入装配 domain 服务

HarnessApplicationConfig 用 60+ 个 @Bean 方法做构造函数注入，domain 服务可脱离容器 new 出来做纯单测。两个参考项目做不到（它们 @Resource 字段注入必须起 Spring 上下文）。

三、dsh-java 优化建议（按优先级）

P0 零事务边界 —— 最严重的架构缺口

现状：全工程 grep -r "@Transactional" 零命中（case/domain/infrastructure 都没有）。

后果实例：EnqueueNode.doApply() 依次调用 openQueuedSession → createQueuedTask → recordTaskSubmission → executeSession，多步写库无任何事务包裹，任一步失败会留下"会话已建但任务未入队"等脏状态。审批落库、插件绑定、模型设置等写路径同理。

三者对比：

  • group-buy-market：infra repository 有 5 处 @Transactional(timeout=500)，至少单聚合操作原子
  • ai-mcp-gateway：infra ProtocolRepository 有 2 处 @Transactional(rollbackFor=Exception.class)，虽不一致但有
  • dsh-java：零

建议（分层施治）：

  1. case 层关键写用例加 @Transactional，包裹跨多仓储的写组合（如 SubmitHarnessTaskCaseImpl.execute、审批 approve 落库）。这是两个参考项目都没做到但应该做到的一层——它们的短板恰好印证了"用例层无事务 = 跨聚合一致性裸奔"。
  2. infrastructure 仓储实现的关键写方法补 @Transactional，保证单聚合内多 DAO 操作原子（对照 group-buy-market 做法）。
  3. 注意：涉及 Agent 长循环（executeSession）的不能用大事务包住整个 turn（会持有 DB 连接数小时），要拆成"短事务 + 事件补偿"。

影响文件：cases/task/submit/node/EnqueueNode.java、cases/agent/AgentUseCase.java、infrastructure/adapter/repository/*

P1 AgentEventListener 空转 —— 事件能力没接通

现状：ReactLoopAgent 构造函数第 10 参 AgentEventListener events，在 AgentFactory.create() 里被传 null → 回退为 NoopAgentEventListener。全仓库除 Noop 外implements AgentEventListener 零实现。

荒谬点：domain 已经有完整的事件溯源设施（ISessionEventStore 双适配器），但 Agent 内部事件（工具调用、turn 开始结束、取消等）根本没有桥接到这个设施。

对照 ai-mcp-gateway：它的 ISessionPort.publishSessionSyncEvent/subscribeSessionSyncEvent 是真正接通的——Redisson 发布订阅在跑，SessionManagementService.cleanupExpiredSessions() 用"本节点静默删除 + 广播 REMOVE 事件"做多实例会话一致性。dsh-java 有更高级的设施却没通电。

建议：

  1. 实现一个真正的 SessionEventAgentListener implements AgentEventListener，在 emit/serial/waterfall 里把 Agent 内部事件桥接到 ISessionEventStore.append()，让事件溯源真正运转。
  2. 在 AgentFactory.create() 里把它作为第 10 参传入，而不是传 null。
  3. 这样 SessionLog 的投影（SurfaceProjector）和回放（SessionRebuilderService）才有真实数据可消费。

影响文件：infrastructure/adapter/agent/AgentFactory.java(:231)、domain/agent/service/AgentEventListener.java、domain/session/event/adapter/repository/ISessionEventStore.java

P1 API DTO 泄漏进 case 层 —— 边界渗漏

现状：case 模块依赖 api 模块，用例方法签名直接吃 api 的 DTO。例如 AgentUseCase.sendMessage(AgentMessageRequest)、SubmitHarnessTaskCaseImpl.execute(SubmitTaskRequest)，都 import net.linlan...api.dto.*。

问题：严格六边形里，用例层应有自己的 Command/Query 对象，由 trigger（controller）层做 RequestDTO → CaseCommand 映射。现在 case 和 api 的 DTO 强耦合，改 api 协议会直接动 case 逻辑，且 case 难以独立测试。

对照：两个参考项目虽也有各自问题，但 ai-mcp-gateway 的 case 层是自持对象（HandleMessageCommandEntity 在 domain，不依赖 trigger DTO）；group-buy-market 的 controller 直接调 domain service，是另一种"没分层"的简单。

建议：

  1. 在 case 模块定义 SendMessageCommand、SubmitTaskCommand 等用例输入对象（纯 POJO）。
  2. trigger/controller 层做 AgentMessageRequest → SendMessageCommand 的映射（加一个 mapper）。
  3. case 模块 pom 去掉对 api 的依赖，恢复 case → {api, domain} 中 api 的关系——或至少让 case 不再直接 import api.dto。

影响文件：cases/agent/AgentUseCase.java、cases/task/SubmitHarnessTaskCaseImpl.java、api/service/*

P2 策略树基类 AbstractStrategyRouter 下沉 domain/shared —— 编排原语泄漏

现状：AbstractStrategyRouter（doApply + getNext 责任链基类）放在 domain/shared/strategy/，case 层的节点继承它。

这是 dsh-java 独有的激进选择：把"流程编排原语"作为领域共享设施。两个参考项目把策略树/责任链放在应用层或外部框架（xfg-wrench 在 types/infra）。

双刃剑：

  • 优点：编排能力可跨 case 复用，节点链装配统一。
  • 缺点：domain 承载了"应用层关注点"（编排），违背"domain 只管业务规则不变量"的纯粹性；case 强依赖 domain 基类，演进时改动面大。

建议（二选一，看团队取向）：

  • 保守派：把 AbstractStrategyRouter 上移到 case 模块的 shared/ 包，domain 不再承载编排原语。参照两个项目的做法。
  • 激进派（保持现状但补文档）：如果团队认可"编排即领域语言"，则保留在 domain/shared，但要在 package-info 里写明设计意图，避免后人误以为是"应该上移的泄漏"。

影响文件：domain/shared/strategy/AbstractStrategyRouter.java、cases/agent/node/*、cases/task/submit/node/*

P2 case 层无 CQRS 物理分离 —— 不如 api 层清晰

现状：api 层已经做了 command/ 和 query/ 包物理分离（api/service/command/*、api/service/query/*），但 case 层没有——只有 cases/session/query/ 一个局部子包，其余混在一起。用例接口命名上区分（ISessionQueryCase vs ISubmitHarnessTaskCase），但物理结构未对齐。

对照：group-buy-market 是"逻辑 CQRS"（读走策略树、写走责任链），ai-mcp-gateway 完全没做。dsh-java 的 api 层已经做得比它们都好，但 case 层没跟上。

建议：如果要走 CQRS 路线，case 层也按 command/、query/ 包组织。查询用例可以走轻量读模型（不重建完整 SessionLog，只投影必要字段），缓解下面的 O(n²) 问题。

P2 deriveMessages 全量重建 O(n²) —— 性能短板

现状：SessionLog.deriveMessages() 注释明确写着 "rebuild from scratch each time"，每次 step 调用都全量重建消息列表 → 长会话累计 O(n²)。token 预算用 length/4 粗估。

对照：两个参考项目没有这种"每步全量重建"的问题——group-buy-market 是请求即响应、无长会话；ai-mcp-gateway 的会话状态靠 Redis 直接存取，不做事件回放重建。

建议：

  • 增量投影：在 SurfaceProjector 里维护增量消息视图，deriveMessages 只追加而非全量重建。
  • 引入 checkpoint：每隔 N 个事件持久化一次快照消息视图，重建时从最近快照开始。
  • 查询路径（CQRS 读模型）直接读快照，不走全量回放。

影响文件：domain/session/event/model/SessionLog.java(:187)、domain/session/event/service/SessionRebuilderService.java

P2 线程池无界 + .join() 阻塞请求线程

现状：ReactLoopAgent.kick() 与 JobRegistryService 都用 Executors.newCachedThreadPool()（无界队列上限 Integer.MAX_VALUE）；ForkInProcessProvider、SpawnInProcessProvider、ToolCallExecutor 用 .join() 阻塞请求线程。

建议：换成有界 ThreadPoolExecutor（明确 core/max/queue capacity + 拒绝策略）；.join() 处加超时（orTimeout）避免请求线程被无限挂住。这是工程健壮性，两个参考项目也没做好（它们线程池配置在 app/config 里但没限流边界），属于通用短板。

影响文件：domain/agent/service/ReactLoopAgent.java(:278)、infrastructure/.../JobRegistryService.java(:25)、infrastructure/.../ToolCallExecutor.java

P2 shell_execute 黑名单无真沙箱

现状：有 DangerousCommandGuard 命令黑名单（命中返回 [sandbox] COMMAND_BLOCKED），但无 OS 级隔离（chroot/容器/资源限制）；执行经 IShellExecutor → ProcessBuilder。

建议：对照 ai-mcp-gateway 的思路（它有 StubE2B* 沙箱抽象但也是 stub），把 IE2BFsPort/IE2BSubprocessPort 从 Stub 实现补成真实现，或在本地用 Linux namespace/cgroup 做轻量沙箱。提交期审批只是第一道闸，执行期应有真隔离。

四、可向两个参考项目借鉴的具体做法

来自 group-buy-market

1. Map<String, Service> 策略选择 —— 零 if-else 路由

它的折扣计算用 @Resource Map<String, IDiscountCalculateService> 按 Bean 名注入，marketPlan 字段取 Bean：

@Resource private Map<String, IDiscountCalculateService> discountCalculateServiceMap;
IDiscountCalculateService svc = discountCalculateServiceMap.get(groupBuyDiscount.getMarketPlan());

dsh-java 的 AgentIntentNode.classify() 是纯正则规则（CHAT/CODE_QUESTION/TASK_EXECUTION/CLARIFICATION），如果意图类型会增长，可借鉴这种 Map 注入式策略路由替代正则硬编码。

2. 责任链用 @Bean 在 Factory 类显式装配

它的 TradeSettlementRuleFilterFactory 用 @Bean 把 SCRuleFilter → OutTradeNoRuleFilter → SettableRuleFilter → EndRuleFilter 串成链，链的顺序一目了然。dsh-java 的节点链靠 @Autowired @Qualifier("下一节点名") 散在各个节点里，链路顺序要逐个文件翻才能拼出来——可以考虑在 Factory 类集中声明链顺序，提升可读性。

来自 ai-mcp-gateway

3. 领域事件端口化（ISessionPort 模式）

它的 ISessionPort 把 publishSessionSyncEvent/subscribeSessionSyncEvent 契约留在 domain，Redisson pub/sub 交给 infra。dsh-java 已有 ISessionEventStore（更强），但缺一个"运行期事件广播"端口——Agent 事件目前只在内存里 no-op。可以再加一个 IAgentEventBusPort（类似 ISessionPort），把"Agent 发生了什么"的实时广播能力端口化，infra 用 Redis/MQ 实现，支持多实例 Agent 协同。

4. 富值对象用 sealed interface + record 做类型安全模型

它的 McpSchemaVO 用 sealed interface JSONRPCMessage permits JSONRPCRequest, JSONRPCNotification, JSONRPCResponse + record，把 JSON-RPC 协议做成类型安全模型。dsh-java 的 ContentBlock、StreamChunk 已经是 sealed 接口（这点做得好），可继续推广这种模式到更多协议模型。

5. 分布式会话治理（nodeId 归属 + 静默删除 + 事件广播）

ai-mcp-gateway 的 SessionManagementService 用 nodeId 归属会话、静默删除 + REMOVE 事件广播做多实例一致性。dsh-java 目前是单实例 Agent Harness，如果将来要多实例，这套治理模型可直接借鉴。

五、落地优先级与小结

优先级事项工作量风险对照参考项目
P0补事务边界（case 层写用例 + infra 仓储关键写方法）中低两个项目都有，dsh 最差
P1接通 AgentEventListener → ISessionEventStore中中（影响 SessionLog 投影）对照 ai-mcp-gateway ISessionPort 已接通
P1case 层引入 Command/Query 对象，去掉对 api DTO 的直接依赖中低ai-mcp-gateway case 自持对象
P2deriveMessages 增量化 + checkpoint大中两项目无此问题（无长会话回放）
P2线程池有界化 + .join() 加超时小低通用短板
P2AbstractStrategyRouter 归位（domain/shared → case/shared 或补文档）小低两项目放应用层/框架
P2case 层 CQRS 包结构对齐 api 层小低dsh 的 api 层已做，case 没跟上
P2shell_execute 真 OS 级沙箱大中ai-mcp-gateway 也是 stub

总结：dsh-java 的 domain 内核设计是三者中最正统的——纯净、充血、事件溯源设施齐全、手工 wire 可测。它不需要学两个参考项目的 domain 设计（那两个的 domain 反而更脏、更贫血）。它真正要补的是：

  1. 工程化焊点（P0 事务、P1 事件接通、P2 线程池/沙箱）——这些是把"骨架最正"兑现成"落地最稳"的关键；
  2. 边界纪律（P1 DTO 泄漏、P2 编排基类归位、P2 CQRS 对齐）——这些是保持 domain 纯净度的长期功课；
  3. 性能（P2 deriveMessages O(n²)）——长会话场景的刚需。

两个参考项目能借鉴的主要是编排范式的可读性（Factory 显式声明链顺序、Map 策略路由）和运行期事件广播端口（ISessionPort 模式补 dsh 缺的那层实时事件总线）。

报告基于对三个项目源码的 very thorough 级核查（2026-09-06）。dsh-java 根包实为 net.linlan.dsh（非 working memory 中的 cn.walioffice，记忆已过期）；提交链实为 5 节点（SubmissionRoot→ProfileResolution→ToolResolution→PermissionCheck→Enqueue），非 3 节点。
